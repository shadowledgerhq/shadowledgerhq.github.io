## 0. Principes

- **Semaine** = de jeudi 01h00 (Europe/Paris) au jeudi suivant 01h00 (exclu). Identifiant = date du jeudi de début (`2026-11-12`).
- **Joueur = chaîne YouTube** (`channel_id`). Le pseudo en jeu (BOT) n'est noté que dans `player_ingame`.
- Seul un **écran RESULT** lu et contrôlé donne un score `exact: true`. Tout le reste (titre, description, sous-titres, légendes, miniature) = provisoire : `exact: false`, `confidence: a_verifier`.
- Seules les runs `confidence: sur` reçoivent un `rank`. Les autres figurent dans le fichier avec `rank: null`.
- Tout paramètre réglable (requêtes, plages, budget, horaires, zones OCR) va dans `pipeline/config/etape1.json`, pas dans le code.
- Chaque donnée de jeu cite sa source et sa date ; une estimation n'est jamais présentée comme un fait.

## 1. Recherche YouTube

### 1.1 Fenêtre de dates
- `debut` = dernier jeudi 01:00:00 Europe/Paris ≤ maintenant, converti en UTC (`zoneinfo("Europe/Paris")`, jamais un décalage fixe). `fin` = maintenant (daily) ou l'instant du reset (weekly).
- Une vidéo publiée avant `debut` n'est jamais rattachée à la semaine en cours ; une vidéo publiée après le reset ne compte jamais pour la précédente.

### 1.2 Sources (dans cet ordre)
1. **Chaînes suivies** (`data/channels.json`) : `playlistItems.list` sur la playlist d'uploads (`UU…`), 50 par page, pages suivantes tant que le dernier élément est publié après `debut` (1 unité/page).
2. **Recherche** : `search.list` (`type=video`, `order=date`, `publishedAfter=debut`, `publishedBefore=fin`, 50 résultats, `q=<requête>`) ; page 2 seulement si le dernier résultat de la page 1 est dans la fenêtre ; 2 pages au plus par requête (100 unités/page).
3. **Détails** : `videos.list` par lots de 50, `part=snippet,contentDetails,liveStreamingDetails` (1 unité/lot).

### 1.3 Filtres
- Exclure `liveBroadcastContent` ≠ `none`, et les rediffusions de live (`liveStreamingDetails.actualStartTime`) → `rejected`, raison `live`. Shorts inclus. Toutes langues, toutes régions.

### 1.4 Requêtes (`config.queries`, par mode)
| Mode | Requêtes |
| --- | --- |
| poc | `solo leveling arise power of calamity` · `solo leveling arise POC` · `나혼렙 재앙의 권좌` · `나 혼자만 레벨업 재앙의 권좌` · `재왕의 권좌` (ancien nom) · `俺アラ 災厄` [À CONFIRMER : nom japonais] |
| bot | `solo leveling arise battlefield of time` · `solo leveling arise BOT` · `나혼렙 시간의 전장` · `俺アラ 時の戦場` |
| gb | `solo leveling arise guild boss` · `나혼렙 길드 보스` · `俺アラ ギルドボス` [À CONFIRMER] |
| hotm | `solo leveling arise hall of the monarchs` [À CONFIRMER] · `solo leveling arise HOTM` · `나혼렙 군주의 회랑` · `俺アラ 君主の回廊` |

- Noms coréens et japonais : inven.co.kr, gamewith.jp/altema.jp (13/11/2026) ; noms anglais non vérifiés.
- Une vidéo trouvée par plusieurs requêtes = une entrée ; le mode de la requête n'est qu'un indice (`mode_guess`), le mode définitif vient de l'écran (§3.1).
- **Faux BOT (v39, `youtube.retirer_faux_bot`, `config.faux_bot.mots`)** : « Battlefield of Infinity », « Battlefield of Chaos », « 無限の戦場 » ne devinent pas le BOT : `bot` est retiré des modes d'une vidéo qui cite l'un de ces mots sans mot du vrai BOT (`config.mode_keywords.bot`). `etape1.relire` corrige aussi les vidéos déjà stockées.
- Une chaîne qui obtient une run classée est ajoutée à `data/channels.json`.

### 1.5 Quota
- `config.quota_max_units = 6000` par passage (sur 10 000/jour), compteur écrit dans le rapport. Erreur `quotaExceeded` : arrêter les recherches, continuer le reste, le signaler.

## 2. Tri 1 — texte

### 2.1 Où chercher
1. Titre et description (API). 2. Sous-titres : **yt-dlp sur le PC** (`--skip-download --write-subs --write-auto-subs --sub-langs "ko.*,ja.*,en.*,fr.*,zh.*"`). 3. Whisper (PC) : seulement sans sous-titre et sans score trouvé.

### 2.2 Formats de nombres (`pipeline/scores.py`, testé)
| Forme | Exemples | Valeur |
| --- | --- | --- |
| Séparateurs de milliers | `131,449,789,393,717` · `131 449 …` (espace, insécable, fine) · `131.449.…` | entier |
| Suffixes latins | `K` 1e3 · `M` 1e6 · `B`/`bn` 1e9 · `T` 1e12 ; décimale `.` ou `,` | arrondi → `exact: false` |
| Coréen | `만` 1e4 · `억` 1e8 · `조` 1e12, cumulables | idem |
| Japonais / chinois | `万` · `億`/`亿` · `兆`, cumulables | idem |
| Chrono (BOT) | `00:19.558` · `0:19` · `19.558s` · `19초` · `19秒` | secondes, 3 décimales |
| Points (HOTM) | `94,600pt` · `94600 points` | entier |
| Rage Count (GB) | `165 RC` · `RC 167` · `332RC` · `Rage Count 165` · `Rage: 159` · `Rage 159` · `159 Rage` (`config.rage_count_mots` = `["rage"]`, mot entier, jamais précédé de `boss`) ; libellés ko/ja [À CONFIRMER] | entier |

- Virgule ou point suivi d'exactement 3 chiffres (et répété) = séparateur de milliers ; sinon décimal.
- **Ignorés** : dates, années, `Lv.`/niv., puissance (`CP`, `전투력`, `戦闘力`, `power`), numéros de porte, durées hors BOT, numéros de saison BOT (`S20-4`).
- **Plages plausibles** (`config.plausible`) : POC 1e12–1e16 (avant la refonte seulement), HOTM 1 000–200 000, BOT 5–180 s, GB 1–500 RC par run ; hors plage = ignoré [à ajuster après quelques semaines].
- **Choix du candidat** : priorité titre > description > sous-titres ; dans une source, le **premier** candidat retenu ; les autres vont dans `notes`.
- **Candidats exclus** : contexte hypothétique (`can`, `could`, `possible`, `up to`, `max`, `~`, `가능`, `可能`, `目標`, `target` : `config.hypothese_mots`) ; chapitres de description (ligne commençant par un horodatage, ou ≥ 2 horodatages croissants) ; au BOT, durée `m:ss` sans millisecondes dans la description.
- **Chrono BOT** : `\d{1,3}[.;:,]\d{3}` suivi ou non de `s` = secondes.millisecondes (`19.558`, `23;223s`) ; jamais un entier. **Virgule + 3 chiffres (`scores.chronos`)** : n'est un chrono que suivi d'une unité (`s`, `sec`, `seconds`, `초`, `秒`) ou écrit `mm:ss,mmm` ; sinon nombre à séparateur de milliers (aucun score). Le point et le point-virgule restent des chronos. Exception : lecture de la **miniature** en chiffres seuls (liste blanche) : `19,926` = 19.926 sans unité, note `miniature : virgule lue comme point` (gardes : chrono isolé, vote, jamais sur une capture Results, écart improbable §4.1, désaccord avec une source précise → `titre/miniature en désaccord`).
- **Chrono BOT incomplet (`pipeline/chrono_bot.py`)** : une lecture sans millièmes (`19s`, `19초`, `Play Time 00:19`) vaut l'intervalle **[N ; N + 0,999]** ; au dixième (`19.9`) [19,900 ; 19,999] ; au centième [19,92 ; 19,929]. Pour une vidéo dont les seules lectures sont provisoires :
  - (a) une lecture **plus précise d'une autre source**, compatible (dans l'intervalle ou partie entière N − 1), la **remplace** : note `titre arrondi : 19s` (ou description / sous-titres) ;
  - (b) sinon la ligne est **triée à la borne haute** (rang prudent), note `chrono incomplet : rang prudent` ; le score affiché reste celui lu ; à clé égale, `published_at` le plus ancien ;
  - (c) lecture précise **incompatible**, ou deux lectures précises à ≥ 1 s : `a_verifier`, note `titre/miniature en désaccord` ; le score affiché reste celui de la source prioritaire (titre > description > sous-titres > miniature) ;
  - un chrono **de texte fini par `00`** (`19.900`) = arrondi au dixième, note `chrono fini par 00 : arrondi probable, à vérifier dans la vidéo` (pas pour un écran Results) ;
  - un joueur à plusieurs vidéos garde sa meilleure run à la clé de tri ; les lectures d'écran `sûr` ne sont jamais touchées.
- **Mots « semaine passée »** (`last week`, `저번 주`, `지난주`, `先週`) dans le titre : note `semaine précédente ?`, `a_verifier`.
- **Mots-clés de mode** : `bot`, `poc`, `gb`, `hotm` en mot entier seulement ; `GB` jamais précédé d'un chiffre (`128 GB`).
- **Relecture** : chaque lecture porte la version des règles (`regles`, `config.tri1_version` = **19**). Une lecture faite avec une version plus ancienne est refaite tant que la vidéo est `en_cours` (titre et description relus via `videos.list`).
- **Dégâts GB du titre** : un titre GB avec RC et dégâts (`64.2 T … 189 rc`) met les dégâts dans `runs_detail[0].damage`, `exact: false` (départage provisoire seulement).
- **Publication proche du reset** : vidéo publiée < `config.reset_alerte_heures` (3 h) après le reset → note `publiée juste après le reset : semaine précédente ?` (alerte, jamais un rejet). Le `Time Left in Season` du Personal Record (GB, §4.7) et `S<n>-<w>` du titre (BOT, §4.6) tranchent.

### 2.3 Statut et marquage
- Tout score du tri 1 est provisoire : `exact: false`, `confidence: a_verifier`, `score_source` = `titre` / `description` / `sous-titres` (jamais `hud` pour un RC). La vidéo passe aux tris suivants jusqu'à lecture de l'écran RESULT.
- **Écran contre titre** : une valeur lue à l'écran et contrôlée (`sur`) prime sur le texte. Si elles diffèrent : note `écart titre/écran : titre <valeur>` ; n'empêche pas `sur`.
- **Actualités probables (`tri1.marquer_hors_sujet`, `config.hors_sujet_mots`)** : un titre qui contient un mot de la liste (sans accents ni casse ; mot entier pour les mots latins, sous-chaîne pour ko/ja/zh) ET aucun score lu dans le texte → `processed[vid].hors_sujet_probable = true`, note « actualités probables (titre) ». **Marquage seulement, jamais un rejet sur le titre seul.** Refait à chaque passage ; disparaît dès qu'un score est lu dans le texte ou que le tri 3 a vu un écran de jeu (`pc.ecran_jeu`). Mots [À VÉRIFIER sur les titres des semaines] : update, patch notes, codes, live, news, leak, resumo, atualização, atualizacao, novidades, 업데이트, 패치노트, 쿠폰, アップデート, 生放送, mecharashi, unstable, summon, gamba, review, hunter archive, dev note, experimento, shorts, #shorts, capitulo, chapter.
- **Durée** (`duree_max_s` = 61) : une vidéo ≤ 61 s n'est marquée que si son `mode_guess` est VIDE **et** son tri 2 est fait SANS score. Une vidéo de mode deviné (BOT : runs de 46 à 50 s) n'est jamais marquée sur la durée, et la durée ne provoque jamais de rejet.
- **Rejet sur le titre (`tri1.mot_rejet_titre`, `pc.rejeter_titre`, `config.rejet_titre.mots`, `config.sla_mots`)** : seul rejet sur le titre = « mecharashi » (autre jeu) ET aucun mot de `config.sla_mots` (solo leveling, arise, 나혼렙, 나 혼자만 레벨업, 俺だけレベルアップ, 我獨自升級) → `rejected`, raison `hors_sujet_titre`, sans sous-titres ni images. « unstable » et les autres mots : marquage seulement.

## 3. Tris 2 à 4 — image

Recadrages OCR : en fractions de l'image (16:9), réglés sur de vraies captures, dans `config.*.zones`. Image au format différent (Short vertical, 4:3, bandes noires) : zones non appliquées, OCR de l'image entière, note `format non standard`. Vidéos verticales (608x1080) : `pas_de_build` à l'étape 2, non réglé [EN ATTENTE d'Alexis].

- **Tri 2 : miniature** (`pipeline/miniature.py`, `maxresdefault` sinon `hqdefault`) : (1) si l'OCR reconnaît un écran RESULT et que le contrôle passe → `sûr` (source `miniature`) ; (2) sinon le texte de la miniature est lu avec les règles du tri 1 → provisoire (`score_source: miniature`, `detail.texte_miniature: true`, note `score provisoire (miniature) : …`). Une fois par vidéo (`processed.pc.tri2` = `fait` | `absent`).
  - **Miniature = capture Results** (`miniature.est_capture_results` : Phase / RESULT / Results / 結果 lu) : jamais lue comme texte, seule la détection d'écran s'applique.
  - **OCR de miniature** : image grise puis masque des pixels blancs (seuils 200, 225), image entière + 6 régions ; au BOT liste blanche `0-9.,:;` (anglais, `psm` 7 et 11), texte libre ailleurs. Un score n'est gardé que si la **même valeur** sort d'au moins `miniature.accord_min` = 2 lectures (3 = `accord_seul` quand la miniature est la seule source ; arrêt à `accord_stop` = 3).
  - **BOT** : seul un **chrono à millièmes isolé** compte (`\d{1,3}[.,:;]\d{3}`) ; un grand nombre à séparateurs de milliers → aucun chrono. Limites connues : minuteur de HUD (`02:29.725`) ou 1re phase d'un Results ; une lecture qui diffère du titre de ≥ 1 s : `titre/miniature en désaccord`. [À CONFIRMER sur passages réels, Windows/tesseract 5.]
- **Tri 3** : 10 premières secondes + 30 dernières, 1 image / 2 s. **Tri 4** : vidéo entière, 1 image / 10 s. Résolution : tri 3 et recherche du Results en **1080p** si dispo (sinon ≤ 1080p), tri 4 en 720p. Une vidéo peut contenir plusieurs écrans RESULT (POC : 2 runs ; compilations) : chaque écran distinct = une run candidate avec `t` (secondes).
- **Décision du tri 3 sur l'image (`pc.traiter_images`, `ocr_ecrans.ecran_de_jeu`)** : pour une vidéo `hors_sujet_probable` ou de plus de `max_minutes` (30), SANS score dans le texte : si **aucune** image du début ni de la fin n'est un écran de jeu du mode (Results, Personal Record, HUD de combat, composition, fiche ; marqueurs `config.ecrans_exclus`) → **rejet** `actualites` (détail « actualités : aucun écran de jeu », `last_tri` 3), sans tri 4 ; lectures retirées. Si un écran de jeu est vu → traitement normal, `hors_sujet_probable` repasse à `false` (`pc.ecran_jeu = true`). Une **page web filmée** (`config.pages_web`) n'est jamais un écran de jeu. Une vidéo > `max_minutes` n'a que le tri 3 (jusqu'à `pc.images.decision_max_minutes` = 240 min [À VÉRIFIER]), puis `tri4` = `inutile`. Une vidéo avec un score dans le texte n'est jamais rejetée sur l'image.
- **Garde contre le rejet à tort** : le rejet `actualites` exige aussi qu'AUCUNE image du début ou de la fin ne « ressemble à un écran de score » (`libelles_inconnus.ressemble_score` : ≥ 3 grands nombres ou un chrono ; page web et écrans exclus vetoés). Si une image y ressemble sans libellé reconnu : pas de rejet, `pc.ecran_score_non_reconnu = true`, note « écran de score non reconnu : à vérifier », passage au tri 4 (sauf > 30 min : tri 3 seul), en dernier dans l'ordre du PC. **Classements de puissance** (« Poder Total », « Categoria de Batalha » : `config.ecrans_exclus.non_mode`) : ni écran de score ni écran de jeu du mode. Rapport du PC : ligne « Téléchargements de décision » (durée vidéo → durée de téléchargement, ou « aucun »).
- **Libellés inconnus** : une image qui ressemble à un écran de score (≥ 3 grands nombres ou un chrono), hors page web et hors écrans exclus, sans libellé reconnu, est collectée dans `docs/essais/ocr/libelles_inconnus/<video_id>_<t>.{txt,jpg}` (3 images au plus par vidéo) ; la discussion 1 en tire les libellés pour `config.*.libelles.<langue>`. Manquent : BOT ko/ja, POC ja, HOTM ja, GB ja, Personal Record ko/pt.
- **Écrans exclus (`config.ecrans_exclus.marqueurs`, comparés sans accents, casse ni espaces)** : jamais un écran de score, plus collectés : `FormTeam`, `Player Mode` (composition BOT, son « Record » est un ancien record), `Total Power`, `Lv.170/170`, `조각상`, `전투력`, `자동 장착`, `My Page`, `Real-time Rank`, « Poder Total », « Categoria de Batalha ». Un écran avec `MANUAL` sans titre `RESULT` / `結果` (HUD de combat du BOT) n'est jamais un écran de score BOT (le HUD du GB reste reconnu par ses libellés).

### 3.1 Écrans par mode

**POC avant la refonte (semaines < 2026-11-19)** : titre RESULT `재앙의 권좌`, libellés `플레이어 스코어`, `계승자 스코어`, `이번 기록`. **POC refonte** : voir §9.

**HOTM** : libellés `클리어`, `증명 보너스`, `합산 결과` (le titre RESULT est le nom du stage). Porte et `hunter_mode` lus sur l'écran de composition par `hotm_ecran.py`.

**BOT** (client anglais) : titre `Results` + nom du boss ; bloc gauche `Phase 1/2/3` avec temps **cumulés** `mm:ss.mmm` (le dernier en cyan) ; bandeau du bas : pseudo en jeu, chrono final, icônes de l'équipe (le losange « 1 » = rang, ignoré ; les 2 icônes après les 3 chasseurs = armes de SJW, qui ne servent plus au classement) ; haut droite `Play Time 00:19` (arrondi). **Score = chrono de la dernière phase = chrono du bandeau.** Jamais le « record » de l'écran de composition.
- **Japonais** : titre `RESULT`, boss dessous, `Phase1/2/3` (sans espace), `進行時間` (= `Play Time` ; variante OCR `信行時間`), `結果` accepté, boutons ignorés (`config.bot.libelles.ja`). Run **sans SJW** : 3 chasseurs au bandeau et zone d'armes vide (preuve d'absence §4.5).
- **Lecture par zone (`config.bot.zones_lecture`, 16:9)** : sur un écran *candidat* (titre `RESULT`/`結果`, ou ≥ 2 temps `mm:ss.mmm`, ou « phase »), recadrage du temps de jeu et de chaque ligne de phase, agrandissement (2,5× / 3×), plusieurs prétraitements (gris, binarisation, masque cyan pour la dernière phase) ; une valeur n'est gardée que si ≥ `accord_min` (2) prétraitements la lisent à l'identique au format strict. Si le temps de jeu est lu ET cohérent (phases croissantes, temps de jeu = dernière phase tronquée), la lecture peut être `sûre`. Deux phases lues suffisent à reconnaître l'écran. Boss non lu dans ce cas (note `boss non contrôlé`).
- **Repli** : temps de jeu illisible mais `RESULT`/`結果` et ≥ 2 temps (ou 2 phases lues) → `a_verifier`, jamais `sûr`, note `BOT ja : temps de jeu non lu`. Temps de jeu incohérent → `a_verifier`, note `contrôle BOT : temps de jeu N ≠ dernière phase tronquée M`.
- **Anti-animation** : un temps n'est gardé que s'il est lu à l'identique sur ≥ 2 images distinctes (`bot.zones_lecture.images_min`, par instant `t`) ; sinon `a_verifier`, note `temps instable (animation ?)`. Une lecture instable dont la 1re phase est celle d'une lecture stable de la même vidéo est écartée (note `lectures instables du même run écartées`). Le chemin « texte entier cohérent avec le bandeau et le temps de jeu » reste `sûr` sur 1 image.
- **Phases incomplètes (`chrono_bot.marquer_borne_basse`, `config.bot.phases_par_boss`)** : sans `Play Time` lu, le dernier temps n'est le chrono que si le nombre de phases lues égale celui du boss (Baruka = 3 ; boss inconnu = 3). Sinon **BORNE BASSE** : `detail.borne_basse`, `detail.sans_score`, `a_verifier`, note `phases incomplètes (2/3) : borne basse 14.515`, jamais un score (ne remplace aucune lecture ; `classement.calculer` l'ignore). Une lecture complète sans `Play Time` reste `a_verifier` et le relevé de rotation ne l'utilise pas (`rotation.chrono_fiable`).
- **Écran en échec de contrôle (`chrono_bot.appliquer_echecs_ecran`)** : un écran dont le contrôle échoue (note `contrôle BOT : …`) ne donne JAMAIS un score (`detail.sans_score`), gardé dans `_lectures.json`, sans remplacer les lectures de texte. `temps de jeu non lu` et `temps instable` ne sont pas des échecs. Cas particulier : si seule la partie entière diffère d'une lecture de texte, et que celle du texte égale le Play Time, la lecture de texte est gardée, `a_verifier`, note `écran : partie entière mal lue (18 → 19 par Play Time et titre)`.

**GB** (boss `Giant Statue` ; libellés par langue dans `config.gb.libelles.<langue>`, jamais en dur) :
- **Écran Results** : titre `Results` + boss, `Player's Score` (SJW), `Successor Score` (si présente), `Hunter Rank` 1 à 6, `Final Score` (dégâts), `Rage Count` (RC), `Play Time 03:00`, bandeau éventuel `New Record Achieved!` (qui peut masquer « Final Score » : Results reconnu aussi par `Hunter Rank` + `Player's Score`/`Successor Score` → `gb_results_partiel`, jamais `sûr` sans Final Score). Il **n'indique pas le groupe**.
- **Une run = un groupe** (`Group 1` / `Group 2`, 6 chasseurs Team A + B + SJW). 2 runs par semaine.
- **Écran `Guild Boss` → `Personal Record`** : `Total Score`, `Challenge Count`, `Total Rage Count`, par groupe RC et dégâts arrondis, `Time Left in Season`. Voir §4.7. `Form Team` : `Score` jamais utilisé.
- **HUD de combat** (jamais un résultat) : `Points` + `Boss Rage Count` `xN` (haut gauche), boss `LV. 150 Giant Statue` (une cible secondaire comme `Temple Altar` n'est pas le boss), chrono décompté depuis `03:00` (`ss.cc` sous 1 min), panneau `Team A/B` (équipe active, ≠ groupe). `Points` + `Boss Rage Count` + chrono sur la même image → mode `gb` confirmé, jamais `sûr`.
  - **`Boss Rage Count` du HUD = information seulement** (`runs_detail[i].hud_rage_count`), jamais un RC.
  - **`Points` du HUD = `Final Score` en cours de run** [À CONFIRMER sur 1 comparaison de plus] : la dernière lecture avec chrono ≤ 5 s donne des dégâts provisoires (`damage_source: hud`, `damage_exact: false`) seulement sans Results ; jamais pour le départage d'une ligne classée ; sert au contrôle du Results. Une lecture HUD incomplète (sans les 3 éléments) est ignorée.
  - **Points plausibles** : entre `gb.hud_points_min` = 1e9 et `gb.hud_points_max` = 1e15, groupes de 3 chiffres complets dans toutes les langues (1er groupe de 1 à 4 chiffres). **Séparateur perdu** : un seul toléré si ≥ 2 séparateurs lus et tous les groupes suivants de 3 chiffres sauf un seul de 6 (note `séparateur perdu (OCR)`). Raison du rejet dans `points_rejet`.

Une zone couvre toute la case (20 caractères) ; un nombre aux groupes de 3 chiffres incomplets est rejeté. La valeur d'une zone prime sur l'image entière (note `écart OCR zone/image : <champ>`). [À CONFIRMER : 3 vidéos de 3 joueurs en 1080p.]

### 3.2 Contrôles
- **POC avant refonte** : `이번 기록` = SJW + successeur + chasseurs 1, 2, 3 → égal : `exact: true`, `sûr` ; sinon `a_verifier`.
- **HOTM** : `클리어` + `증명 보너스` = `합산 결과` = `이번 기록` → `sûr`. `증명 보너스` = niveau × 100 : alerte seulement (`notes`).
- **BOT** : dernière phase = chrono du bandeau, `Play Time` = ce chrono tronqué à la seconde, phases croissantes → `exact: true`, `sûr` ; sinon `a_verifier`.
- **Pseudo en jeu (BOT)** → `player_ingame`.
- **GB** : `Player's Score` (+ `Successor Score`) + 6 `Hunter Rank` = `Final Score` → `exact: true`, `sûr`. Hunter Rank illisibles : contrôle de remplacement (§3.1). Pas de contrôle arithmétique du RC.
- **GB, RC confirmé par le Personal Record** : si le contrôle de somme est sauté (`Player's Score` en conflit ou illisible), le RC reste `sûr` si (a) RC stable sur ≥ 2 images sans conflit, (b) égal au RC d'UN groupe d'un Personal Record `sûr` de la MÊME vidéo (`Total Rage Count` = somme ; `Time Left` cohérent), (c) aucun RC contradictoire dans le titre ni dans le HUD de fin (un RC de HUD SUPÉRIEUR au Results contredit ; inférieur ou égal = normal). Dégâts = `Final Score` voté, `damage_exact: false`, `exact: false`. Note `RC confirmé par le Personal Record ; contrôle de somme impossible (Player's Score illisible)`. Une somme calculée fausse n'est jamais contournée. **Jamais** de `Player's Score` déduit de Final − somme des rangs, ni de concordance par la fin des chiffres.
- **GB, garde-fou du vote des dégâts** : si la somme échoue ou est sautée, `damage_exact: false` ET le dégât ne départage jamais une égalité de RC : deux lignes `sûr` de même RC total dont l'une a un dégât non contrôlé → cette ligne passe `a_verifier`, note `égalité départagée par un dégât non contrôlé` (`classement.ordonner`).
- Jamais `기존 기록`, jamais le score de l'écran de composition.

## 4. Calcul du classement (`pipeline/classement.py`, idempotent)

### 4.1 Une ligne par joueur
- Clé : `channel_id` (+ `gate` au HOTM). On rassemble toutes les runs `sur` du joueur dans la semaine, toutes vidéos confondues.
- **BOT** : meilleur chrono, un seul classement (§4.6). **HOTM** : meilleur score **par porte** (un fichier par porte).
- **Borne basse BOT (`chrono_bot.appliquer_bornes_basses`)** : ne sert que de contrôle d'une lecture provisoire de la même vidéo : lecture < borne → `a_verifier`, note `provisoire inférieur à la borne basse de l'écran` ; sinon note `borne basse de l'écran 14.515 : compatible`. Ne remplace jamais une lecture.
- **Publication tant que « Top 10 couvert » = non** : l'Excel (§5.6) et le site montrent les lignes `sûr` ET les provisoires dans l'ordre de tri commun (BOT : rang prudent compris), les provisoires marquées « À vérifier ». Le rang officiel (`rank`) n'est affiché que s'il n'est précédé d'aucune ligne non sûre. Top 10 couvert = `ordre_pc.candidates_restantes` = 0 ; inconnu = non. Le site applique la même règle [EN ATTENTE].
- **POC (avant refonte) et GB : total = somme des 2 meilleures runs distinctes** (groupes ou équipes distincts), toutes vidéos de la semaine du joueur confondues. Le POC refonte suit §9.
  - POC avant refonte : une run = une équipe (`1팀` / `2팀`) ; total = meilleure run de l'équipe 1 + meilleure de l'équipe 2 ; équipe illisible : les 2 meilleures runs en `a_verifier` ; deux runs de la même équipe ne s'additionnent jamais.
  - GB : classement au **Rage Count** : RC de la meilleure run du groupe 1 + RC de la meilleure du groupe 2. « Meilleure » = RC le plus élevé, puis dégâts (`Final Score`). Groupe illisible : les 2 meilleures en `a_verifier`. Égalité de RC total : départage par la **somme des dégâts** des 2 runs, puis §4.2. `score.total`/`score.runs` = RC (`unit: rage_count`) ; dégâts dans `runs_detail[i].damage` ; `team` = groupe (1, 2 ou `null`).
  - **GB : runs filmées seulement** : une run GB n'est classée que si un écran **Results** est lu dans la vidéo. Le HUD seul reste provisoire. Le **Personal Record ne classe aucune run** ; seul : aucune run classée, note de rapport « Personal Record seul : aucune run filmée » (`res.records_seuls`) ; la vidéo continue ses tris. Un RC du titre reste provisoire.
  - **Une seule run** : une ligne avec une seule run `sur` est classée (`confidence: sur`, `rank`), total = cette run, note `une seule run` ; une 2e run (autre groupe / équipe) trouvée plus tard s'ajoute. Une seule run provisoire → `a_verifier`.
  - **Groupe / équipe d'une run**, dans cet ordre : (a) GB : le RC du Results égal au RC d'**un seul** groupe du Personal Record `sûr` de la **même vidéo** → groupe attribué (`team`, note `groupe N d'après le Personal Record (RC égal)`) ; POC : l'équipe lue à l'écran. (b) Sinon l'**élément** de la run (`pipeline/elements.py`) : (1) élément majoritaire des chasseurs vus (`detail.hunter_ids`, identifiants de `data/db/hunters.json` ; [À VÉRIFIER] pas encore alimenté de façon fiable) ; (2) sinon l'élément cité par le titre, s'il en cite un seul et que la vidéo n'a qu'une run filmée du mode ; (3) titre à 2 éléments et vidéo à 2 runs : chaque élément va à la run dont les chasseurs l'ont ; si une seule run est lue et que son élément figure au titre, l'autre reçoit l'élément restant ; sinon pas d'association. Mots du titre (`config.elements_titre`, sans accents ni casse, [À VÉRIFIER]) : Light/Lumière/Luz/光/빛 · Fire/Feu/Fogo/Fuego/火/불 · Water/Eau/Água/Agua/水/물 · Wind/Vent/Vento/Viento/風/바람 · Dark/Ténèbres/Trevas/Oscuridad/闇/암흑. (c) Deux runs d'un même joueur sont de groupes / équipes **différents** si leurs éléments diffèrent et qu'aucun chasseur commun n'est vu ; un chasseur commun vu = même groupe, sans exception. **L'écran prime sur le titre** : contradiction → `a_verifier`, note `élément du titre contredit par l'écran`.
  - **Mots d'élément d'un caractère** (빛 불 물 光 火 水 風 闇) : seulement **isolés** (début/fin de titre, espace, ponctuation ou chiffre autour ; `水篠旬`, `괴물`, `화상` ne comptent pas). 명 et 화 non ajoutés.
  - **Élément lu sur le HUD** (`pipeline/elements_hud.py`, `config.elements_hud` [À CALIBRER]) : couleur du losange d'élément de chaque portrait du panneau d'équipe (centres 1920×1080 : x≈1725, y≈356 / 452 / 548) ; vus : fire ≈ 0°, light ≈ 44-52°, wind ≈ 87-120° ; **water et dark jamais vus**. Élément de la run = élément strictement majoritaire avec ≥ 2 losanges concordants sur ≥ 2 images, sinon `null` (`element_source: ecran`). **Priorité : `hunter_ids` > `elements_hud` > titre.** Contradiction avec le titre → `a_verifier`.
  - **`detail.hunter_ids`** : (a) build `sûr` de l'étape 2 de la même run (même vidéo et mode, `t_result` à ≤ 10 s) ; sinon (b) portraits des 6 lignes « Hunter Rank » du Results (`pipeline/hunters_results.py`) comparés à une banque apprise `data/icons/hunters_results/<id>-<n>.png` (4 au plus par chasseur), qui ne se remplit que quand l'identité vient de (a) (appariée aux cartes `data/icons/hunters_cartes/<id>[--tenueN].png`). Banque vide = `hunter_ids` absent, note `chasseurs reconnus : n/6`. POC : zones du RESULT [À CALIBRER].
  - **Total GB / POC avant refonte** = la meilleure **paire** de runs de groupes / équipes distincts. Runs distinguées par l'élément : s'additionnent sans numéro (`team: null`). Ligne `sûr` si les deux runs sont `sûr` et qu'aucune lecture d'écran ne contredit le titre. Notes : `groupes distingués par les chasseurs`, `groupes distingués par le titre (Light / Fire)`, `élément associé titre + chasseurs`. Plusieurs runs `sur` de groupe inconnu **jamais additionnées** : classée avec la meilleure run seule, note `groupes inconnus : 2e run non additionnée (<RC>, <video_id>)`. Équipe lue d'un côté seulement : additionnées, `a_verifier`.
- **Écart improbable (`classement.ordonner`, `chrono_bot.ecart_improbable`)** : (BOT) un score provisoire de texte < 70 % de la médiane des scores provisoires de la semaine (≥ 5 lignes provisoires) ; (GB, v39) parmi les lignes non `sûres`, un RC < 70 % de la médiane des RC provisoires (≥ 5 lignes), quelle que soit la source. La ligne reste dans le fichier mais en fin de liste, note `écart improbable : à confirmer par l'écran`, hors du top 10 provisoire (`builds.modes_du_top`, donc ni builds provisoires ni top 3 de la rotation) tant qu'un écran ne l'a pas confirmée ; la vidéo reste candidate pour le PC.
- **Relecture automatique (`pipeline/relectures.py`)** : au début d'un passage PC (hors `--video`), toute vidéo BOT ou GB des **10 premières lignes** non `sûres` de `bot.json` / `gb.json`, `status: termine`, `pc.results_lus` vide, `regles` < `tri1_version`, est remise `en_cours` (`pc_needed`, `pc.tri3`/`tri4` = `a_faire`, `relecture` = date). **Un seul passage par vidéo et par version** (`processed[vid].relecture_auto`). Ligne du bloc : `Relectures posées (règles plus anciennes, top 10 provisoire sans Results lu) : <id> (<mode>), …`. **Relectures explicites (`config.relectures_manuelles`, `relectures.poser_manuelles`)** : une fois par version (`processed[vid].relecture_manuelle`) ; `relecture_dernier` = traitée après toutes les autres, jamais comptée dans « Top 10 couvert ».

### 4.2 Égalité
1. Le joueur dont le score a été **complet le plus tôt** passe devant (`published_at` le plus récent des vidéos utilisées). 2. Dernier recours : `channel_id` alphabétique. (POC refonte : ex aequo, §9.)

### 4.3 Arrondis
Un score provisoire est remplacé dès qu'une run exacte du même joueur est lue ; jamais additionné à une run exacte.

### 4.4 Doublons et ré-uploads
- Seulement pour `config.doublon_modes` = `["poc"]`. Même score exact, même mode = même run : même chaîne → comptée une fois ; chaînes différentes → à la vidéo **la plus ancienne**, la run en trop est retirée de l'autre (rejetée `doublon`, `detail` = video_id d'origine, seulement si elle n'a plus aucune run). Au POC refonte : l'équipe est dans la clé (deux lectures de même score d'équipes différentes ne sont pas des doublons).
- BOT et HOTM : pas de dédoublonnage automatique ; même score sur 2 chaînes → les deux gardées, note `doublon possible : <video_id>`, contrôle manuel (discussion 1).

Vidéo publiée < `config.bot.reset_boss_heures` (6) h après le reset dont le boss diffère de la référence → `rejected`, `semaine_precedente` (detail = boss lu) ; boss identique → la note « publiée juste après le reset » est retirée. - **Éléments autorisés** (`data/rules/<semaine>.json`) **déduits des écrans**, jamais saisis à la main : `true` dès qu'**une** run `sûr` le montre (POC : ligne SJW et successeur ; GB : `Player's Score`, `Successor Score` ; BOT : 2 icônes d'armes de SJW ; HOTM : composition) ; `false` seulement si ≥ 5 runs `sûr` de 5 chaînes le montrent absent (note `déduit, à vérifier`), sinon `null` ; jamais `false` sur une vidéo. `sjw_skills`, `blessings`, `shadows` suivent la même règle avec pour preuve le build reconnu de l'étape 2 (`found` à true) ; `sjw: false` → `sjw_skills` et `blessings` false (note `déduit de sjw: false`), jamais l'inverse. **Absence de SJW au BOT** : seule preuve = zone des 2 armes lue vide (`config.bot.zone_armes_sjw`) sur ≥ 5 runs sûres de 5 chaînes. ### 4.7 GB : écran `Personal Record`
- **Ne classe aucune run** (§4.1). Il reste lu et contrôlé, et sert à attribuer un groupe à un Results de même RC dans la même vidéo.
- **Contrôle** : `Total Rage Count` = RC groupe 1 + RC groupe 2 → RC `sûr` (`score_source: record`), sinon `a_verifier`. `Total Score` (exact) est gardé dans `runs_detail`.
- **Recoupement du `Total Score`** : il doit être proche de la somme des dégâts arrondis des groupes (écart ≤ l'arrondi affiché) ; sinon il est écarté (note `contrôle Personal Record : Total Score <valeur> incohérent avec les dégâts des groupes`), les RC restent `sûr` si Total = somme.
- **Bonne semaine** : `Time Left in Season` (ex. `6d 9h`) : capture = prochain reset − temps restant ; si elle tombe **après** `published_at` + marge, le record date de la saison précédente → `rejected`, `semaine_precedente`. Marge = plus petite unité affichée (heures → 60 min `config.gb.record_tolerance_minutes` ; jours seulement → 24 h ; minutes → 1 min). Illisible → `a_verifier`. Contrôle du boss (§4.5) comme ailleurs.
- **Groupe sans run** : `Group 2  No history` = groupe non joué (pas une lecture manquante ; `team` connu). - **Rattachement d'une run Results à un groupe** : (1) RC et dégâts arrondis égaux à ceux d'un seul groupe → ce groupe ; (2) RC égal à celui d'un seul groupe et dégâts supérieurs à son record → ce groupe (nouveau record) ; (3) sinon `team: null`.
